# Roadmap

A status snapshot and prioritized next steps — not a promise or a schedule, just a living plan for a solo project. This repo stays private until the owner decides otherwise.

**This file is the durable source of truth for project state and decisions** — kept deliberately thorough so that pulling this repo fresh (a different machine, a new AI coding session with no memory of prior conversations, etc.) is enough to pick up where things left off without re-deriving context. If you're an AI assistant reading this cold: read this whole file plus `docs/protocol.md` before making architectural changes: several of the "obvious" simplifications (e.g. "just always call `update_character`", "just use full history") were deliberately rejected below, with reasons.

## Current state (done)

- Single-player skeleton: WebSocket server + Textual client, strict turn queue.
- Persistence: session state survives server restarts; the client remembers its own identity across restarts so it reconnects as the same character.
- Chat (`/chat <text>`) and dice rolls (`/roll <NdM[+/-K]> [reason]`) wired end-to-end, both exempt from turn order.
- DM narration behind a swappable `NarratorBackend` (`server/narrator.py`): `AnthropicNarrator` (hosted Claude) and `OllamaNarrator` (`server/narrator_ollama.py`, free local model). Both support tool use: a local SRD lookup tool (`server/rules/`, CC-BY-4.0 dataset) for consistent mechanics, and `update_character` for real HP/inventory/condition changes. Only `AnthropicNarrator` also has `web_search` — that's an Anthropic-hosted server tool with no local equivalent.
- **DM memory**: a rolling window of the last 6 turns (`Session.append_turn`, `MAX_HISTORY_MESSAGES` in `server/state.py`) is threaded through as real conversation history on every `narrate()` call, replacing the old single-last-turn-only context. Chosen over full history (unbounded cost growth) and a summary hybrid (more complexity than needed right now) explicitly because of the no-spend stance.
- **Real consequences**: an `update_character` tool (HP delta, add/remove inventory, add/remove a condition) the DM calls whenever narration should mechanically change the acting character. The engine applies it via `CharacterSheet.apply_update()` and pushes `character_update` to that player only when something actually changed (a no-op call, e.g. `hp_delta: 0`, doesn't spam an update). `CharacterSheet` gained a `conditions` field for this; the client sheet panel now renders it.
- CI, a 44-test suite, MIT license (with the SRD data separately CC-BY-4.0 attributed), issue/PR templates.

- **NPC/monster state tracking.** Closes the exact gap the "Re-verified live" entry above flagged as still open: previously `update_character` only ever touched the acting player's own sheet, so a wounded NPC's HP existed only in that turn's prose — nothing stopped the DM from narrating a goblin at 3 HP one turn and full HP the next, since there was nothing to check against. `update_character`'s input gained an optional `target` field: omitted (or `"self"`) is the unchanged existing behavior; a name is an NPC — the first call for a given name creates a tracked sheet in the new `Session.npcs` dict (reusing `CharacterSheet` as-is, no new model), defaulting `max_hp` to 10 (the same fallback `join_session` already uses for a fresh player) if the DM doesn't pass a real value from `lookup_rule`; every later call with that same name updates the same tracked NPC. A new `npc_update` envelope (`{name, sheet_delta}`) broadcasts to *everyone* on a real change — deliberately not routed privately like `character_update`, since an NPC's wounds are shared observable fiction, not one player's private sheet. `state_sync` now includes `npcs` too, so a (re)joining player sees current NPC state immediately. The Textual client renders NPC status as a dim log line (`goblin: HP 3/7`) rather than a new dedicated panel — a deliberately small UI footprint for a first pass, revisit if it turns out to need more. 8 new engine-level tests (target dispatch, introduction vs. update, no-op-doesn't-rebroadcast, persistence across turns, `state_sync` inclusion); one real gap caught immediately by running them: `shared/protocol.py`'s `Envelope.type` is a strict pydantic `Literal` that didn't yet include `"npc_update"` — every construction raised a `ValidationError` until it was added alongside `character_update`.
- **DM-mediated dice rolls (`request_roll`), Anthropic-only for now (2026-08-07).** Previously `/roll` was entirely player-initiated and completely disconnected from the DM — the narrator never requested a roll, never set a DC, and never adjudicated success/failure from one; narration and mechanics were decided independently of anything actually rolled. A new `request_roll` tool (dice notation, optional `dc`, optional `reason`) lets the DM ask for a roll before narrating an uncertain outcome, get back a real result (plus a success/failure verdict if a `dc` was given), and narrate to match it rather than deciding the outcome first and rolling to match after the fact. `GameEngine._on_player_action` gained a `request_roll` closure (mirroring `apply_update`'s existing pattern) that rolls via the existing `dice.roll()`, tracks what was rolled, and broadcasts both a visible `dice`-kind `log_entry` and a `dice_result` envelope after narration completes — reusing and extending (not duplicating) the exact same broadcast shape `_on_dice_roll` already used for manual `/roll`, via two new shared helper methods (`_dice_log_text`, `_dice_result_envelope`). **Deliberately scoped to `AnthropicNarrator` only**: `REQUEST_ROLL_TOOL` is in its tool list, but *not* in `OllamaNarrator`'s `OLLAMA_TOOLS` — this session's investigation (see item 6) found `qwen2.5:7b`/`llama3.1:8b` already miss the one existing required tool call on most clearly-warranted turns, so adding a second required tool-call step before narration would only compound that, not help. `OllamaNarrator.narrate()` accepts the `request_roll` parameter for interface parity (`NarratorBackend` Protocol) but never wires it to a real tool, so local models cannot call it at all — not just "less reliable at it." 9 new tests across `test_narrator.py`, `test_narrator_ollama.py`, and `test_engine.py` (tool dispatch, the deliberate Ollama exclusion, dc/no-dc broadcast shape, invalid-notation handling). **Not yet verified live** — `AnthropicNarrator` as a whole is still only structurally tested against mocked responses, same gap as item 2 below; this adds to what that live verification needs to cover, it doesn't close it.
- **Immersion pass: persistent world state, quest log, NPC memory, opening hook (2026-08-07).** Motivated by open research into comparable AI-GM projects and papers this session (function-calling AI GMs, solo-RPG agentic-vs-static comparisons, the closest open-source sibling project `open-tabletop-gm`) — the converging finding was that structured, *persistent* world/plot state, not just character state, is what makes a session feel like a story worth following rather than a chatbot answering one prompt at a time. Before this, `WorldState` existed but was nearly inert (a free-text `summary`, unused `flags`), `CharacterSheet.notes` existed but nothing ever set it, and nothing happened on session start beyond silence until the player acted.
  - **`update_world` tool, Claude-only (same reasoning as `request_roll` above).** `WorldState` gained a real `apply_update()` (mirroring `CharacterSheet.apply_update()`'s exact pattern) and a new `objectives: list[Objective]` field (`Objective` = `{text, status: "active"|"completed"}`). The tool supports `location`, `summary` (a standing 1-3 sentence campaign summary, not per-turn detail), `add_objective`/`complete_objective`/`remove_objective` (matched by exact text), and `set_flag`/`clear_flag`. Broadcasts a new `world_update` envelope (broadcast, not private - shared fiction like `npc_update`) on a real change. Not in `OLLAMA_TOOLS`, for the same reliability reasoning as `request_roll`.
  - **NPC memory via `CharacterSheet.notes`, both backends.** The `notes` field already existed on the model but nothing ever set it. `UPDATE_CHARACTER_TOOL`'s schema (shared by both backends - not Claude-gated, since it's the *existing* tool, not a new one) gained a `notes` parameter, and `CharacterSheet.apply_update()` now handles it (overwrite-if-changed, same pattern as the other fields). Both system prompts now tell the DM to give a new NPC a brief note on introduction (personality/goal/relationship) and update it if the relationship changes, so a recurring character feels continuous instead of reset each time they reappear.
  - **An opening scene on genuine campaign start, both backends.** `_on_join_session` now detects a real campaign start (a brand-new character *and* an empty session log - not just a later player joining an in-progress one) and narrates a short opening scene before the first `turn_prompt`, instead of leaving the player facing silence until they act first. Reuses the exact same narration/tool-wiring path as a real turn (via a new shared `_narrate_and_apply(character, action_text)` helper factored out of `_on_player_action`), so the DM can use `update_world`/`lookup_rule` to set an initial location or objective right at the start, exactly like any other turn. Doesn't consume the turn queue (no `advance_turn()`); best-effort - a failure sends a warning `system_message` rather than blocking the join. Gated behind a new `GameEngine(..., enable_opening_scene=True)` constructor flag (default on) specifically so the reliability harness's fixed 8-turn scenario (which expects each turn to map to exactly one `narrate()` call) and the large majority of pre-existing engine tests, which relied on `join()` having no narration side effect, didn't all need rewriting - only the tests and harness scenario that predate this feature explicitly opt out.
  - **Client**: `CharacterSheetPanel` now also renders active objectives (below inventory/conditions, same list style), fed from `state_sync`'s already-present-but-previously-unused `world_state` payload and the new `world_update` envelope. No new panel/CSS - reuses the existing sheet panel, same "small footprint for a first pass" approach as the NPC status lines.
  - 15 new tests across `test_state.py`, `test_narrator.py`, `test_narrator_ollama.py`, and `test_engine.py` (`WorldState`/notes `apply_update()` behavior, tool dispatch, the deliberate Ollama exclusion, `world_update` broadcast shape, opening-scene firing-once/not-on-rejoin/failure-handling, the test helper's default-off regression guard). Client rendering reviewed by inspection only — no client-side test infrastructure exists in this repo to extend.
  - **Deliberately deferred**: background world-ticks (NPCs/factions advancing off-screen between sessions) and a relationship graph (who-knows-whom, surfaced by `open-tabletop-gm`'s design) — both real ideas from the same research, but bigger and more speculative; this pass builds the smallest slice that directly closes the "nothing persists, nothing happens on its own" gap first, matching this project's own "measure the smallest real slice" discipline throughout this session.
  - **Not yet verified live** — same `AnthropicNarrator` gap as `request_roll` above (no `ANTHROPIC_API_KEY` configured in the dev environment this was built in); structurally tested against mocks only. A live Ollama regression run confirmed the `_narrate_and_apply` refactor itself didn't change existing turn behavior.
- **Client crash on modern Textual, found while capturing README screenshots (2026-08-07).** `CharacterSheetPanel` (`client/app.py`) defined its own private helper method named `_render` — which silently shadows `Widget._render()`, an internal method Textual's layout engine calls on every widget to compute content height. The override returned `None` (it just called `self.update(...)` as a side effect) instead of a `Visual`, so any layout pass touching the sheet panel before its first `update()` call — which is every app startup, since the panel is empty until the first `state_sync` — crashed with `AttributeError: 'NoneType' object has no attribute 'get_height'`. Confirmed via a minimal repro (a bare `Static` subclass with only a same-named `_render` method reproduces it in isolation) that this is a real name collision, not a version-support gap: the currently-installed Textual (8.2.8, well past this project's `textual>=0.58` floor) calls `self._render()` from `get_content_height()`; older Textual apparently didn't hit this exact path the same way, which is presumably why it went unnoticed in day-to-day use. Fixed by renaming the helper to `_refresh_display`. All 88 tests still pass; verified live end-to-end afterward via a real headless session against `qwen2.5:7b` (see Screenshots in the README). Worth a `textual` upper/lower bound revisit given a patch-level-invisible framework change was able to crash the app outright.
- **Silent persistence failure discovered on a long-running dev server, startup writability check added (2026-08-07).** A `server.main` process that had been running continuously since 2026-08-06 (pre-dating this repo's move from `~/Documents/ai-dungeon-master` to its current `~/Projects/github/oracle` location) was still alive with its `cwd` pointed at the now-deleted old directory - Linux keeps a process's cwd handle valid even after the directory itself is unlinked, so the process kept running normally, but `SESSION_STORE_DIR`'s default relative path (`"sessions"`) resolves against that dead cwd. Every `_save()` since has been raising `FileNotFoundError: 'sessions/default.json'` with nothing surfaced to the player - a live, real character's entire session (multiple turns of narration, HP loss, an NPC encounter) existed only in that process's memory, one restart away from total loss, discovered only by directly reading the server's own log for a traceback. **Fixed the class of failure this represents, not just this one incident**: `JSONFileSessionStore.__init__` (`server/persistence.py`) now does a real write-and-delete probe against its directory, not just `mkdir(parents=True, exist_ok=True)` (which is a silent no-op against an already-existing-but-unwritable directory, and wouldn't itself have caught this incident's actual failure mode either, since `sessions/` had genuinely existed under the old path at some point). Raises a new `SessionStoreUnwritable` with a clear, actionable message; `server/main.py` catches it and exits with a one-line logged error instead of a raw traceback. 2 new tests (`tests/test_persistence.py`): a read-only existing directory, and a read-only parent blocking directory creation. **Known limitation, not solved by this fix**: a startup check only catches a *misconfigured* store directory - it does nothing for this incident's actual shape, where the directory was valid at startup and disappeared later, mid-process-life. That would need every `_save()` call site to handle a save failure as a visible, non-fatal `system_message` (matching the pattern `_on_player_action`'s narration-failure handling already uses) instead of letting it propagate into an unhandled exception that silently kills that connection - not yet done; flagged as a real follow-up below, not assumed closed by this entry.
- **A related, unexplained client crash observed live in that same session, cause not confirmed.** While driving a few manual turns against that same long-running (pre-fix) server to check for issues, the interactive Textual client process - and, since it was tmux's only remaining pane, the whole tmux server with it - exited within seconds of a `/roll 1d20` command being sent. `dmesg`/`journalctl` showed no OOM-kill or crash signature, just systemd logging the pane's scope ending normally; no core dump, and the pane's own stderr died with it, so there's no traceback to inspect. Timing is suspicious but not proof - noted here rather than either ignored or overclaimed as a confirmed `/roll`-handling bug. - **`.env` was never actually being read - the entire README setup flow silently did nothing, found while confirming a clean session works end-to-end (2026-08-07).** Every config read in this codebase (`DM_BACKEND`, `ANTHROPIC_API_KEY`, `OLLAMA_MODEL`, `SESSION_ID`, ...) is a plain `os.environ.get(...)`; nothing anywhere called `load_dotenv()` or equivalent, despite the README's own setup instructions being "`cp .env.example .env`, then fill in the lines that matter." A freshly-created `.env` with `DM_BACKEND=ollama` had zero effect - `create_narrator()`'s `os.environ.get("DM_BACKEND", "anthropic")` fell through to the hardcoded `"anthropic"` default every time, and with no `ANTHROPIC_API_KEY` ever exported either, every single narration call (including the opening scene) failed immediately with `TypeError: Could not resolve authentication method`. This had been silently swallowed by the same missing-exception-logging gap noted just above (the very fix that let this be diagnosed at all, on the first real attempt after adding it) - without that log line, this would have looked identical to the qwen2.5:7b flakiness this project has spent an entire investigation on, and very nearly got misdiagnosed as exactly that before the traceback showed a completely unrelated Anthropic SDK auth path being hit instead of Ollama. **Fixed**: added `python-dotenv` (`pyproject.toml`), `server/main.py` now calls `load_dotenv()` as the first line of `main()`, before anything reads `os.environ` - additive only, a real `export`ed value still wins over `.env`. Verified live end-to-end afterward: fresh session, `DM_BACKEND=ollama` from `.env` alone (no exports), opening scene generated correctly via Ollama, `sessions/default.json` saved with real log/history content. All 94 tests still pass. Worth noting this bug is presumably not new - it's very plausibly been present since `.env.example` itself was first added, silently defeating that entire section of the README for however long, until this session's own exception-logging fix (immediately) and manual live testing (immediately after) happened to catch it together.
- **Live smoke-testing on the newly GPU-verified machine (see GPU migration readiness, below) reproduced a fresh instance of the known leaked-pseudo-tool-call failure and caught a genuine gap in the missed-change heuristic meant to guard against it (2026-08-07).** Driving a handful of manual turns against `qwen2.5:7b` on the GPU: a combat turn ("I draw my sword and attack the shadowy figure") narrated a `add_condition: "frozen"` outcome ("chilling your skin", "a numbing cold spreading") but printed it as a literal JSON blob in the narration text (`Update your sheet: {"add_condition": "frozen", ...}`) instead of making a real `update_character` call - confirmed via the server log showing only **one** `httpx` request for that turn, where a genuine tool-call round trip needs two, the same diagnostic this project has used throughout. The opening scene on this same run also printed a paraphrased instruction-like preamble ("Update your sheet to reflect your current state:") before otherwise-normal narration - not verbatim from any prompt text, a hallucinated stage direction rather than a copied string, matching the "leaked raw internal instruction text" category already noted elsewhere in this file as a known detection gap. **A real, fixable bug found alongside this**: `POSSIBLE_UNTRACKED_CHANGE_PATTERN`'s own comment states its intent as "damage/death/condition language," but the actual regex had zero condition-related keywords - so this exact turn's clearly-condition-changing narration never tripped the missed-change warning it exists to provide. **Fixed**: added `condition`, `poison(ed/ing)`, `stun(s/ned/ning)`, `paraly(zed/zing/sis)`, `frozen`, `freez(e/es/ing)`, `chill(s/ed/ing)`, `numb(s/ed/ing)`, `blind(ed/ing)`, `burn(s/ed/ing)`, `prone`, `restrained` to the pattern (`server/engine.py`). 1 new regression test (`tests/test_engine.py`) reconstructing this exact scenario's narration text. All 95 tests pass. The underlying leaked-JSON/tool-avoidance behavior itself is unchanged - this closes a real gap in the *detection* heuristic, not the model's own reliability, which remains item 6's open investigation. Separately confirmed clean during the same session: `/roll`, `/chat`, and a genuinely non-mechanical action (opening a door) all behaved correctly with no false-positive warning.

The owner's own words: *"i did not see character sheet for my character information"* - a real, first-hand confirmation of the gap, not a hypothetical one. **Fixed with a deliberately small, deterministic slice** - not a full 5e character builder: `join_session`'s payload gained an optional `character_class` (`fighter`/`wizard`/`rogue`/`cleric`, the four classes already in the SRD dataset, `server/rules/srd.json`). - **Case-insensitive NPC name matching (2026-08-08), closing the "Remaining candidates" item flagged under item 6 below.** `Session.npcs` was keyed by the exact raw `target` string the DM's `update_character` call sent; a name that came back re-cased on a later turn (`"Bandit"` after an earlier `"bandit"` - exactly what a live `qwen2.5:7b` split-experiment run actually did, see item 6) would silently create a second, disconnected NPC entry rather than updating the one already tracked, rather than a hypothetical. **Fixed in `GameEngine._narrate_and_apply`'s `apply_update` closure (`server/engine.py`)**: NPC lookup/storage now keys off `target.casefold()` (`npc_key`), while the `CharacterSheet.name` set at introduction keeps the original first-seen casing - so a re-cased later call updates the existing tracked NPC instead of duplicating it, and the tool result / `npc_update` broadcasts stay consistent under whichever casing introduced the NPC, not whatever casing a later call happens to use. `_state_sync_envelope`'s `npcs` payload was keyed the same way (raw dict iteration) and got the same fix - now keyed by `npc.name` rather than the (now-casefolded) internal dict key, so a reconnecting client's status lines match what live `npc_update` broadcasts already show. 2 new tests (`tests/test_engine.py`): a re-cased target on a later turn updates the existing NPC rather than duplicating it, and `npc_update` broadcasts keep the first-seen name across a recase. Full suite green (105 tests; the 2 pre-existing `test_persistence.py` `chmod`-based unwritable-directory failures are a root-user sandbox artifact - `chmod 0o500` doesn't block root - confirmed unrelated by reproducing them against an unmodified checkout).

5. **Follow-up investigation, one session later: streaming ruled out, history-driven degradation confirmed, one candidate fix tried and reverted after it didn't hold up under real-engine testing.**
   - **Streaming was a real, tempting suspect — ruled out empirically, not assumed.** `ollama-python`'s own GitHub issues (#279, #12557, #9632) document real streaming+tool-calling bugs — tool-call data landing in `content` instead of `tool_calls`, inconsistent chunking — matching this project's exact `stream=True` usage closely enough to be a plausible root cause. Checked directly against this project's real installed version (`ollama` 0.6.2) rather than assumed from the issue reports: a minimal single-shot request (no history) correctly returned a real `tool_calls` entry with `stream=True`, every time. A second, harder test — the same request but with a realistic 6-turn rolling-history window prepended, matching a real mid-session turn — got a real tool call only **1 of 4 times** with `stream=True`, and the *identical* history-heavy request with `stream=False` also got **1 of 4** — same rate either way. Streaming is not the cause.
   - **The real, confirmed lever is accumulated conversation history, not streaming.** The minimal no-history case worked every time tested; the realistic history-heavy case dropped to ~25% regardless of streaming. This matches a well-known small-model pattern: instructions placed once at the start of a long context (the system prompt's tool-use policy) can lose effective weight relative to more recent content as that context grows — a real, if still not fully explained, mechanism worth keeping in mind for future investigation (e.g. of the deferred "revisit memory if sessions run long" item above).
   - **A second, distinct problem found in the same history-heavy testing: mistargeting, not just missing calls.** When a tool call *did* fire under history-heavy conditions, it sometimes targeted the acting character (`'self'`, or the character's own name) even though the narration was entirely about an NPC being killed by that character's own attack — a real semantic error, not just an omission.
   - **A candidate fix — a short, explicit reminder repeated at the end of every turn's own prompt (not just once in the system prompt), disambiguating "target = whoever got hurt, not whoever acted"** — was designed and tested in two stages. Stage one, isolated diagnostic testing (single requests, no real engine involved): the reminder fixed the mistargeting cleanly (0/2 correct targets without it, 2/2 with it, in back-to-back small batches) with call-rate roughly unchanged (~40% either way). Promising enough to implement for real and verify against the actual production code path, not just the isolated snippet — this project's own standard, applied here deliberately before claiming a fix.
   - **Stage two — implemented in `server/narrator_ollama.py`, then re-ran the *exact same* 8-turn scenario from item 4's second pass above, through the real `GameEngine`/`OllamaNarrator`, for a direct before/after comparison. Result: not a net improvement, and a new, more visible defect appeared.** The engine-measured success rate was still **0 of 8** — identical to the no-reminder run, no actual improvement in what matters (state getting tracked). But narration in 6 of the 8 turns now contained a literal, player-visible line like `update_character {"target": "Bandit", "hp_delta": -8}` — the model expressing its tool-call intent as leaked text in the story itself, rather than through Ollama's real function-calling channel, where `apply_update` would have actually run. This exact leaking pattern was **not present at all** in the no-reminder run of the identical scenario — a new regression the fix introduced, not something already there. Interestingly, the *reasoning* visible inside that leaked text mostly got the target right (`"Bandit"` for enemy damage, the character's own name only for the genuinely self-inflicted turns) — weak evidence the reminder did influence the model's reasoning about *who*, just not *how* to actually invoke the tool, and arguably made the visible failure mode worse (exposed raw mechanics to the player) instead of better.
   - **Decision: reverted, not shipped.** A change that doesn't measurably improve the metric that matters (real invocations reaching `apply_update`) and introduces a new, more immersion-breaking visible defect isn't a fix, regardless of what the isolated diagnostic suggested. `server/narrator_ollama.py` and its tests are back to exactly what they were before this investigation started. The reminder's exact wording is preserved here in case a future attempt wants a documented starting point, not because it's believed to be close to correct:
     ```
     (Reminder: if this turn's outcome changes anyone's HP, inventory, or
     conditions, call update_character now. target must be whoever actually
     got hurt or changed, not simply whoever acted - if the acting character
     attacks someone else and that other creature takes the damage, target
     is that NPC's name, never the acting character's own name or 'self'.
     Only use 'self' when the acting character is the one taking damage or
     being changed.)
     ```
   - **What's actually been ruled out vs. still genuinely open, for whoever picks this up next**: ruled out — streaming as the cause (confirmed via direct A/B test against the real installed `ollama` version), and this specific reminder-based fix (confirmed via real-engine before/after testing). Still open — *why* history accumulation degrades tool-use this much, whether a structurally different intervention (e.g. two separate requests — one forcing a tool-use decision with no narration, then a second for the narration itself, rather than one combined request) would fare better, whether a different/larger local model changes this materially, and whether the same history-driven pattern affects Anthropic's Claude backend at all (still fully unverified live, pending API credits — see item 2 above).

- **A scene "mood"/environment tag on `WorldState`**, alongside its existing `location`/`summary` — cheap to add now, and sets up a real hook for the image-generation item below to key an image prompt off of a short structured tag rather than parsing raw narration text.
- **`dice_result` client rendering** (`docs/protocol.md` "Known client gap"): the Textual client has no handler for the structured `dice_result` envelope — manual/DM-requested rolls are only visible via their accompanying plain-text `log_entry` line. Small, self-contained fix (a few lines in `client/app.py`'s `_handle()`), just not yet prioritized over the reliability/immersion work. The concrete payoff once this is fixed: highlighting a natural 20/1 in the client, currently impossible since the structured roll data never reaches client-side rendering logic at all.
- **A distinct visual treatment for the new missed-change warning** (the visible-mitigation heuristic shipped above) vs. every other `system_message` — the client currently renders all system messages identically, but this one is a different category (an advisory the player should weigh, not a connection/turn-order error) and reads oddly styled the same as one.
- **A real NPC status panel**, replacing the "dim log line" the immersion-pass entry (Current state, above) itself flagged as a deliberately small first-pass UI footprint — revisit now that NPC tracking has had more real play time behind it.
- **A session-transcript export in the client** — save the running narration log to a plain text file. Cheap, no model/GPU/API dependency, direct value for a solo player who wants a record of their story; a good candidate for the "terminal-UI improvements now" track ahead of any web-client work.
- **Presentation polish for the README/GitHub page**, candidate ideas from a 2026-08-07 pass that added the real screenshots currently in `docs/screenshots/` — none started, purely options to pick from later:
  - A short animated demo (`asciinema` recording → `svg-term` render, or a GIF) instead of/alongside the two static screenshots, to show narration actually streaming in rather than just a before/after pair.
  - A custom Textual `CSS`/theme for `DungeonMasterApp` (`client/app.py`) — right now it's the framework default palette with a plain `$accent`-bordered box layout; a theme suited to a tabletop/parchment feel would read as more intentional in a screenshot.
  - An HP bar or similar small visual indicator on `CharacterSheetPanel` instead of the current plain `HP: 10/10` text line.
  - A simple wordmark/banner for the top of the README — currently just an `# Oracle` heading plus badges.
- **Make a mid-session `_save()` failure visible instead of an unhandled exception**, closing the known limitation the 2026-08-07 startup-writability-check entry (Current state, above) explicitly left open. Right now every `_save()` call site (`_on_join_session`, `_narrate_opening_scene`, `_on_player_action`) lets a save failure propagate uncaught, which just kills that connection with nothing shown to the player - the startup check catches a misconfigured directory at boot, but not this same directory going away later, mid-process-life (the exact incident that prompted this note). Fix shape: wrap `_save()` similarly to how `_on_player_action` already handles a narration failure - catch, send a `system_message` warning the player their progress isn't being saved, and keep the turn going rather than dropping the connection.
### GPU migration readiness (2026-08-07)

**Migration completed and verified live (2026-08-07).** Original plan below assumed "a 2080 Ti — 11GB VRAM" sight unseen; the machine actually used is a laptop (`msi-laptop`, reached over the LAN, not this project's usual dev machine) with an **RTX 2080 with Max-Q Design — 8GB VRAM (7.6 GiB reported available), CUDA compute 7.5, driver 610.43.03**, correcting that assumption now that real hardware is in hand rather than leaving the old guess standing.

- **No Oracle code changes were needed** - confirms the "zero application-level changes" expectation below held in practice, not just in theory. Ollama was installed user-locally (`~/.local/ollama`, no root - the official installer's own `sudo` steps didn't work non-interactively over this SSH session, so the plain release tarball was extracted and symlinked into `~/.local/bin` instead), the repo copied over via `rsync` (this repo is still private, and `gh` wasn't installed on the target machine), and a normal `pip install -e '.[ollama,dev]'` in a fresh venv. All 94 tests passed unmodified.
- **GPU pickup confirmed, not assumed**: `ollama serve`'s own startup log reported `library=CUDA ... name="NVIDIA GeForce RTX 2080 with Max-Q Design" ... type=discrete total="7.6 GiB"`, and `ollama ps` during a real narration call showed `100% GPU` - exactly the smoke check this section called for before trusting any results transfer.
- **Real speedup measured, not estimated**: a cold first call (`qwen2.5:7b`, opening-scene-shaped prompt) took 55.8s - almost entirely one-time model-load-into-VRAM overhead, not representative of steady-state - but two warm calls immediately after took **1.5s and 1.7s**, at 36-40 words/sec. Against this project's own documented CPU baseline (30-90s/turn throughout every experiment in this file), that's roughly a **20-40x per-turn speedup** once the model is loaded. Verified end-to-end through the real engine too, not just the narrator in isolation: a live join/opening-scene/turn cycle through the actual `server.main`/`client.main` over a real websocket connection worked cleanly, session persisted correctly to `sessions/default.json` on this new machine (the writability-check and `.env`-loading fixes earlier in this same file both verified working on a second, independent machine as a side effect).
- **8GB VRAM, not 11GB - re-scopes the "what fits" estimate below.** `qwen2.5:7b` (4.7GB file) fit with headroom (7.5 GiB free reported at load). `qwen2.5:14b`'s ~9GB Q4_K_M file is close to or past the 7.6 GiB ceiling and hasn't been tried on this machine yet - worth an explicit test rather than assuming it fits or spills to CPU gracefully, since the original "11GB comfortably fits 7-14B" framing doesn't hold as-is on this specific card.
- **What a GPU actually unlocks for the reliability work already underway**: CPU-only inference is the reason every experiment this session has taken 5-20+ minutes per model per scenario (30-90s+ per turn, worse for `qwen3:8b`'s thinking mode) — that latency is *why* this project has only ever run one scenario, one time, per model. A GPU makes the kind of statistical rigor the current methodology can't afford practical: repeated runs of the same scenario per model to quantify sampling variance (exactly the "run it again to confirm" request that prompted this note), multiple distinct scenarios instead of one, and testing genuinely large models (`qwen2.5:32b`+, `qwen3:14b`/`32b`) that are impractical to even attempt on CPU. The measured 20-40x per-turn speedup above makes this concretely practical now rather than a future aspiration - re-running item 6's `--repeat` experiments on this machine is the natural next step, not yet done as part of this migration itself.
- **`--repeat N` harness flag: built (2026-08-07), ahead of GPU migration rather than waiting for it.** `scripts/live_reliability_check.py` now runs the scenario N times against the same model and reports both a mean-of-rates and a pooled rate with the per-run spread (e.g. `run 1/3: 2/7 (29%)`, `run 2/3: 1/7 (14%)`, ... `mean of per-run rates: 21%`), instead of a single-sample point estimate — directly closes the "one true positive isn't proof" gap the `qwen3:8b` result above ran into by hand. `--out` with `--repeat > 1` writes a JSON report shaped `{repeat, aggregate, runs: [[...], [...]]}` rather than the single-run shape, via new `run_stats()`/`aggregate_stats()`/`write_json_repeat()` functions (6 new tests, `tests/test_live_reliability_check.py`, using a fresh `ScriptedNarrator` per simulated run). Built now, while still CPU-only, because the owner's structural-readiness goal ahead of a planned GPU move (see above) is exactly this kind of "have the tooling ready before the hardware makes it cheap to use" work — each repeat still costs as much wall-clock time as a single run today, so using `--repeat` with anything above 2-3 remains impractical until then, but the capability no longer needs to be built later under time pressure.
- **Image generation, revisited**: local Stable Diffusion (via ComfyUI, InvokeAI, or a bare `diffusers` script) is impractical on this project's current CPU-only dev hardware — text generation alone is already slow at 30-90s/turn; image diffusion on pure CPU is typically far slower per image. An `ImageBackend` protocol (mirroring `NarratorBackend`'s existing swappable-interface pattern) with a local ComfyUI/SD implementation becomes realistic on an 11GB GPU. A hosted alternative (OpenAI, Stability AI, Replicate, etc.) would still be a legitimate separate backend for users without a GPU, same relationship as `AnthropicNarrator`/`OllamaNarrator` today — paid+fast vs. free+hardware-dependent.
