# Roadmap

A status snapshot and prioritized next steps — not a promise or a schedule, just a living plan for a solo project. This repo stays private until the owner decides otherwise.

**This file is the durable source of truth for project state and decisions** — kept deliberately thorough so that pulling this repo fresh (a different machine, a new AI coding session with no memory of prior conversations, etc.) is enough to pick up where things left off without re-deriving context. If you're an AI assistant reading this cold: read this whole file plus `docs/protocol.md` before making architectural changes: several of the "obvious" simplifications (e.g. "just always call `update_character`", "just use full history") were deliberately rejected below, with reasons.

## Current state (done)

- Single-player skeleton: WebSocket server + Textual client, strict turn queue.
- Persistence: session state survives server restarts; the client remembers its own identity across restarts so it reconnects as the same character.
- Chat (`/chat <text>`) and dice rolls (`/roll <NdM[+/-K]> [reason]`) wired end-to-end, both exempt from turn order.
- DM narration behind a swappable `NarratorBackend` (`server/narrator.py`): `AnthropicNarrator` (hosted Claude) and `OllamaNarrator` (`server/narrator_ollama.py`, free local model). Both support tool use: a local SRD lookup tool (`server/rules/`, CC-BY-4.0 dataset) for consistent mechanics, and `update_character` for real HP/inventory/condition changes. Only `AnthropicNarrator` also has `web_search` — that's an Anthropic-hosted server tool with no local equivalent.
- **DM memory**: a rolling window of the last 6 turns (`Session.append_turn`, `MAX_HISTORY_MESSAGES` in `server/state.py`) is threaded through as real conversation history on every `narrate()` call, replacing the old single-last-turn-only context. Chosen over full history (unbounded cost growth) and a summary hybrid (more complexity than needed right now) explicitly because of the no-spend stance.
- **Real consequences**: an `update_character` tool (HP delta, add/remove inventory, add/remove a condition) the DM calls whenever narration should mechanically change the acting character. The engine applies it via `CharacterSheet.apply_update()` and pushes `character_update` to that player only when something actually changed (a no-op call, e.g. `hp_delta: 0`, doesn't spam an update). `CharacterSheet` gained a `conditions` field for this; the client sheet panel now renders it.
- CI, a 44-test suite, MIT license (with the SRD data separately CC-BY-4.0 attributed), issue/PR templates.
- **A real narration round-trip has been verified**, live, via Ollama — not just mocked, across five real turns total, two models compared head to head on the *same session* (same character "Torvin Ironheart", same rolling history):
  - **`llama3.1:8b`** — turn 1: correct, real `update_character` call (`hp_delta: -1`, the model's own judgment, no injury explicitly prompted). Turn 2, given "I approach the hooded figure and ask what they are drinking": did **not** call the tool at all — instead wrote its reasoning about calling the tool as plain narration text, including a literal fake `{"name": "update_character", "parameters": {...}}` JSON blob that leaked straight into the shared log, and broke character ("To answer this question, we need to update the character's sheet...") despite the system prompt explicitly saying never to. Confirmed via the server log that only one API request was made that turn (a real tool round-trip needs two) — Ollama's actual function-calling mechanism was never invoked; the model just role-played having a tool.
  - **`qwen2.5:7b`** — tried next, on the same session/character (now at HP 9/10 after the llama3.1 turns), specifically to see if a different model was more reliable at this. Turn 3, "I draw my sword and attack the hooded figure": correct, real tool call, `hp_delta: -4`, narration coherent (a magical flash, a shallow wound, the figure escaping), no leaked JSON, stayed in character. Turn 4, "I sheath my sword and look around" (deliberately non-mechanical, to test *precision* not just recall): correctly made **no** tool call — single API request, HP unchanged, clean narration. Turn 5, "I press a cloth against my wound to try to stop the bleeding" (a genuinely ambiguous case — first aid stops bleeding but doesn't typically restore HP without a proper check/spell): again correctly made **no** tool call. Three out of three clean, including one non-trivial judgment call, not just easy no-ops.
  - Minor style quirk noted on turn 5, not a correctness bug: narration ended with a numbered multiple-choice menu ("1. Ask the bartender... 2. Look around...") rather than open-ended prose. The system prompt asks for natural narration inviting the next action, not a menu — worth a prompt tweak if this recurs (e.g. explicitly say "no numbered option lists").
  - Sample size is still small (3 turns for qwen2.5:7b, 2 for llama3.1:8b) — not a rigorous benchmark, just enough signal to change the default. `qwen2.5:7b` is now `OllamaNarrator`'s default model (`server/narrator_ollama.py`, and `.env.example`'s `OLLAMA_MODEL`).
  - CPU-only inference (no GPU on the dev machine — 12 cores, 125GB RAM, integrated Intel graphics only) is slow either way: roughly 30-90s per turn.
  - The hosted Claude backend (`AnthropicNarrator`) shares the identical engine/tool-loop code path but hasn't been run live yet — still pending account credits.
- **Prompt tweak**: both `DM_SYSTEM_PROMPT` (`server/narrator.py`) and `OLLAMA_SYSTEM_PROMPT` (`server/narrator_ollama.py`) now explicitly say narration should end in open-ended prose, never a numbered/bulleted list of options — closes the turn-5 menu quirk noted above.
  - **Re-verified live** against `qwen2.5:7b`, two more turns (new session — no prior `sessions/` state existed on this machine — same character "Torvin Ironheart", reconstructed at HP 9/10 to continue the fiction): turn "swing my longsword at the bandit blocking the doorway" and turn "glance around the room to see what else is here." Neither ended in a numbered/bulleted list — the tweak holds so far, though the prior quirk was already rare (1 of 5 turns), so 2 more clean turns is weak-but-positive evidence, not proof.
  - Neither turn actually exercised `update_character`, and correctly so on inspection, not a miss: turn 1's damage landed on the bandit (an NPC), not on Torvin, and this engine only tracks the acting player's own sheet — no HP delta was owed. So this pair adds two more turns to the "no call needed, no call made" column, not a new positive-call data point; item below is still open.
  - Minor style oddity, not a correctness bug: turn 1's narration ended with a bare "Update?" rather than inviting the next action — worth watching for recurrence, not urgent enough to act on from a single instance.
- **NPC/monster state tracking.** Closes the exact gap the "Re-verified live" entry above flagged as still open: previously `update_character` only ever touched the acting player's own sheet, so a wounded NPC's HP existed only in that turn's prose — nothing stopped the DM from narrating a goblin at 3 HP one turn and full HP the next, since there was nothing to check against. `update_character`'s input gained an optional `target` field: omitted (or `"self"`) is the unchanged existing behavior; a name is an NPC — the first call for a given name creates a tracked sheet in the new `Session.npcs` dict (reusing `CharacterSheet` as-is, no new model), defaulting `max_hp` to 10 (the same fallback `join_session` already uses for a fresh player) if the DM doesn't pass a real value from `lookup_rule`; every later call with that same name updates the same tracked NPC. A new `npc_update` envelope (`{name, sheet_delta}`) broadcasts to *everyone* on a real change — deliberately not routed privately like `character_update`, since an NPC's wounds are shared observable fiction, not one player's private sheet. `state_sync` now includes `npcs` too, so a (re)joining player sees current NPC state immediately. The Textual client renders NPC status as a dim log line (`goblin: HP 3/7`) rather than a new dedicated panel — a deliberately small UI footprint for a first pass, revisit if it turns out to need more. 8 new engine-level tests (target dispatch, introduction vs. update, no-op-doesn't-rebroadcast, persistence across turns, `state_sync` inclusion); one real gap caught immediately by running them: `shared/protocol.py`'s `Envelope.type` is a strict pydantic `Literal` that didn't yet include `"npc_update"` — every construction raised a `ValidationError` until it was added alongside `character_update`.
- **DM-mediated dice rolls (`request_roll`), Anthropic-only for now (2026-08-07).** Previously `/roll` was entirely player-initiated and completely disconnected from the DM — the narrator never requested a roll, never set a DC, and never adjudicated success/failure from one; narration and mechanics were decided independently of anything actually rolled. A new `request_roll` tool (dice notation, optional `dc`, optional `reason`) lets the DM ask for a roll before narrating an uncertain outcome, get back a real result (plus a success/failure verdict if a `dc` was given), and narrate to match it rather than deciding the outcome first and rolling to match after the fact. `GameEngine._on_player_action` gained a `request_roll` closure (mirroring `apply_update`'s existing pattern) that rolls via the existing `dice.roll()`, tracks what was rolled, and broadcasts both a visible `dice`-kind `log_entry` and a `dice_result` envelope after narration completes — reusing and extending (not duplicating) the exact same broadcast shape `_on_dice_roll` already used for manual `/roll`, via two new shared helper methods (`_dice_log_text`, `_dice_result_envelope`). **Deliberately scoped to `AnthropicNarrator` only**: `REQUEST_ROLL_TOOL` is in its tool list, but *not* in `OllamaNarrator`'s `OLLAMA_TOOLS` — this session's investigation (see item 6) found `qwen2.5:7b`/`llama3.1:8b` already miss the one existing required tool call on most clearly-warranted turns, so adding a second required tool-call step before narration would only compound that, not help. `OllamaNarrator.narrate()` accepts the `request_roll` parameter for interface parity (`NarratorBackend` Protocol) but never wires it to a real tool, so local models cannot call it at all — not just "less reliable at it." 9 new tests across `test_narrator.py`, `test_narrator_ollama.py`, and `test_engine.py` (tool dispatch, the deliberate Ollama exclusion, dc/no-dc broadcast shape, invalid-notation handling). **Not yet verified live** — `AnthropicNarrator` as a whole is still only structurally tested against mocked responses, same gap as item 2 below; this adds to what that live verification needs to cover, it doesn't close it.
- **Immersion pass: persistent world state, quest log, NPC memory, opening hook (2026-08-07).** Motivated by open research into comparable AI-GM projects and papers this session (function-calling AI GMs, solo-RPG agentic-vs-static comparisons, the closest open-source sibling project `open-tabletop-gm`) — the converging finding was that structured, *persistent* world/plot state, not just character state, is what makes a session feel like a story worth following rather than a chatbot answering one prompt at a time. Before this, `WorldState` existed but was nearly inert (a free-text `summary`, unused `flags`), `CharacterSheet.notes` existed but nothing ever set it, and nothing happened on session start beyond silence until the player acted.
  - **`update_world` tool, Claude-only (same reasoning as `request_roll` above).** `WorldState` gained a real `apply_update()` (mirroring `CharacterSheet.apply_update()`'s exact pattern) and a new `objectives: list[Objective]` field (`Objective` = `{text, status: "active"|"completed"}`). The tool supports `location`, `summary` (a standing 1-3 sentence campaign summary, not per-turn detail), `add_objective`/`complete_objective`/`remove_objective` (matched by exact text), and `set_flag`/`clear_flag`. Broadcasts a new `world_update` envelope (broadcast, not private - shared fiction like `npc_update`) on a real change. Not in `OLLAMA_TOOLS`, for the same reliability reasoning as `request_roll`.
  - **NPC memory via `CharacterSheet.notes`, both backends.** The `notes` field already existed on the model but nothing ever set it. `UPDATE_CHARACTER_TOOL`'s schema (shared by both backends - not Claude-gated, since it's the *existing* tool, not a new one) gained a `notes` parameter, and `CharacterSheet.apply_update()` now handles it (overwrite-if-changed, same pattern as the other fields). Both system prompts now tell the DM to give a new NPC a brief note on introduction (personality/goal/relationship) and update it if the relationship changes, so a recurring character feels continuous instead of reset each time they reappear.
  - **An opening scene on genuine campaign start, both backends.** `_on_join_session` now detects a real campaign start (a brand-new character *and* an empty session log - not just a later player joining an in-progress one) and narrates a short opening scene before the first `turn_prompt`, instead of leaving the player facing silence until they act first. Reuses the exact same narration/tool-wiring path as a real turn (via a new shared `_narrate_and_apply(character, action_text)` helper factored out of `_on_player_action`), so the DM can use `update_world`/`lookup_rule` to set an initial location or objective right at the start, exactly like any other turn. Doesn't consume the turn queue (no `advance_turn()`); best-effort - a failure sends a warning `system_message` rather than blocking the join. Gated behind a new `GameEngine(..., enable_opening_scene=True)` constructor flag (default on) specifically so the reliability harness's fixed 8-turn scenario (which expects each turn to map to exactly one `narrate()` call) and the large majority of pre-existing engine tests, which relied on `join()` having no narration side effect, didn't all need rewriting - only the tests and harness scenario that predate this feature explicitly opt out.
  - **Client**: `CharacterSheetPanel` now also renders active objectives (below inventory/conditions, same list style), fed from `state_sync`'s already-present-but-previously-unused `world_state` payload and the new `world_update` envelope. No new panel/CSS - reuses the existing sheet panel, same "small footprint for a first pass" approach as the NPC status lines.
  - 15 new tests across `test_state.py`, `test_narrator.py`, `test_narrator_ollama.py`, and `test_engine.py` (`WorldState`/notes `apply_update()` behavior, tool dispatch, the deliberate Ollama exclusion, `world_update` broadcast shape, opening-scene firing-once/not-on-rejoin/failure-handling, the test helper's default-off regression guard). Client rendering reviewed by inspection only — no client-side test infrastructure exists in this repo to extend.
  - **Deliberately deferred**: background world-ticks (NPCs/factions advancing off-screen between sessions) and a relationship graph (who-knows-whom, surfaced by `open-tabletop-gm`'s design) — both real ideas from the same research, but bigger and more speculative; this pass builds the smallest slice that directly closes the "nothing persists, nothing happens on its own" gap first, matching this project's own "measure the smallest real slice" discipline throughout this session.
  - **Not yet verified live** — same `AnthropicNarrator` gap as `request_roll` above (no `ANTHROPIC_API_KEY` configured in the dev environment this was built in); structurally tested against mocks only. A live Ollama regression run confirmed the `_narrate_and_apply` refactor itself didn't change existing turn behavior.

## Next — highest priority, in rough order

1. **Revisit memory if sessions run long.** The rolling window (last 6 turns) fixes the "forgets what just happened" problem completely but still forgets anything older than the window — a very long session could still see the DM drop an early plot thread or NPC. Not worth solving until it's actually observed happening in play; the fix, if needed, is a summary of everything outside the window, kept updated via a DM tool call the same way `update_character` works.

2. **Verify the hosted Claude path live too**, once there's a way to (credits, or just to compare narration quality against the local models side by side) — the code path is identical to Ollama's. Would also be useful as a reliability baseline: Claude is specifically trained for reliable tool use in a way small local models aren't always, so this comparison would show whether `llama3.1:8b`'s turn-2 flakiness (see above) was purely a small-local-model thing or something more general. Now also the only way to verify `request_roll` (see Current state, above) actually works end-to-end — it's Anthropic-only and still unverified beyond mocked tests.

3. **`qwen2.5:7b`'s earlier "3-for-3" framing no longer holds — a much bigger live sample (see item 4) found a real, substantial drop in tool-call reliability.** That "3-for-3" was 3 turns, all on the simple `self`-target path, in a short session. It's since been contradicted by a much larger, harder sample. Correcting the record here rather than leaving the old framing standing: across every live `qwen2.5:7b` turn run against this project so far (13 total, spanning three separate sessions), only 2 of roughly 8 clearly-warranted calls actually happened. See item 4 for the full breakdown — this item is kept separate to flag explicitly that the original claim was too optimistic, not just incomplete.

4. **NPC/monster state tracking, live-verified twice against `qwen2.5:7b` — a real, substantial tool-call reliability gap found, not yet fixed or explained.**
   - **First pass (2 turns, one session, one NPC):** turn 1 narrated real damage to a bandit but never called `update_character` at all; turn 2 did call it correctly (`target="bandit"`, proving the dispatch mechanism itself works end-to-end), but the narration's own stated HP arithmetic ("health drops from 7 to 1") didn't match what was actually applied (`hp=4`, `max_hp=10` — there was no real prior "7," since turn 1's call never happened), and two lines of raw internal instruction text leaked verbatim into the in-character prose (*"Deal 6 damage to the bandit on a hit."*, *"Update the bandit's HP and add a new condition (wounded)..."*).
   - **Second pass (8 turns, one session, two sequential bandits, deliberately mixing NPC-target/self-target/non-mechanical actions):** **zero `update_character` calls across all 8 turns** — not one, on either the NPC or `self` path. This includes turns 1, 2, 4, 5, and 6, all of which narrated a bandit taking unambiguous, eventually lethal damage ("driving his longsword deep into the bandit's gut... life drains from his form") with no ambiguity about whether something mechanical happened. Turns 3 and 8 (pure observation/looting) correctly warranted no call; turn 7 (pressing a cloth to a wound, no proper healing) is genuinely ambiguous, same as the original comparison's turn 5. Unlike the first pass, this run's narration stayed clean — no leaked instruction text — it simply never reached for the tool at all, a different failure shape than the leaking seen before.
   - **The honest combined tally, not smoothed over**: across all three live sessions this project has run against `qwen2.5:7b` (13 turns total — 3 from the original head-to-head, 2 from the first NPC pass, 8 from the second), only 2 of the turns that clearly warranted a call actually got one. The 3 clean self-target turns from the original comparison are still real and still stand, but they no longer represent the model's overall behavior once NPCs and longer combat sequences enter the picture.
   - **A real, unresolved question, not a conclusion**: whether this is specific to NPC-targeting (a newer tool-input shape than plain `update_character`, genuinely less represented in whatever this model was trained on) or a broader degradation as a session's rolling history grows (the second pass's 8 turns is longer than any prior live test, and the *later* turns weren't noticeably worse than the earlier ones — turn 1 already missed). The data so far doesn't cleanly separate these two hypotheses, since every clearly-mechanical turn in the second pass happened to be an NPC-target case (Torvin was never narrated as taking damage himself). Worth a future session that mixes in genuine `self`-target damage partway through a longer combat sequence, specifically to tell these two explanations apart.
   - **Not fixed this session, deliberately** — matches this project's own standard of logging a real finding rather than iterating prompts until a clean run happens to appear. Whatever the fix turns out to be (a prompt change, a smaller/different history window, or accepting this as a known limitation of a free local 7B model), it should be designed against a clearer picture of *why* this is happening, not against this one data point.

5. **Follow-up investigation, one session later: streaming ruled out, history-driven degradation confirmed, one candidate fix tried and reverted after it didn't hold up under real-engine testing.**
   - **Streaming was a real, tempting suspect — ruled out empirically, not assumed.** `ollama-python`'s own GitHub issues (#279, #12557, #9632) document real streaming+tool-calling bugs — tool-call data landing in `content` instead of `tool_calls`, inconsistent chunking — matching this project's exact `stream=True` usage closely enough to be a plausible root cause. Checked directly against this project's real installed version (`ollama` 0.6.2) rather than assumed from the issue reports: a minimal single-shot request (no history) correctly returned a real `tool_calls` entry with `stream=True`, every time. A second, harder test — the same request but with a realistic 6-turn rolling-history window prepended, matching a real mid-session turn — got a real tool call only **1 of 4 times** with `stream=True`, and the *identical* history-heavy request with `stream=False` also got **1 of 4** — same rate either way. Streaming is not the cause.
   - **The real, confirmed lever is accumulated conversation history, not streaming.** The minimal no-history case worked every time tested; the realistic history-heavy case dropped to ~25% regardless of streaming. This matches a well-known small-model pattern: instructions placed once at the start of a long context (the system prompt's tool-use policy) can lose effective weight relative to more recent content as that context grows — a real, if still not fully explained, mechanism worth keeping in mind for future investigation (e.g. of the deferred "revisit memory if sessions run long" item above).
   - **A second, distinct problem found in the same history-heavy testing: mistargeting, not just missing calls.** When a tool call *did* fire under history-heavy conditions, it sometimes targeted the acting character (`'self'`, or the character's own name) even though the narration was entirely about an NPC being killed by that character's own attack — a real semantic error, not just an omission.
   - **A candidate fix — a short, explicit reminder repeated at the end of every turn's own prompt (not just once in the system prompt), disambiguating "target = whoever got hurt, not whoever acted"** — was designed and tested in two stages. Stage one, isolated diagnostic testing (single requests, no real engine involved): the reminder fixed the mistargeting cleanly (0/2 correct targets without it, 2/2 with it, in back-to-back small batches) with call-rate roughly unchanged (~40% either way). Promising enough to implement for real and verify against the actual production code path, not just the isolated snippet — this project's own standard, applied here deliberately before claiming a fix.
   - **Stage two — implemented in `server/narrator_ollama.py`, then re-ran the *exact same* 8-turn scenario from item 4's second pass above, through the real `GameEngine`/`OllamaNarrator`, for a direct before/after comparison. Result: not a net improvement, and a new, more visible defect appeared.** The engine-measured success rate was still **0 of 8** — identical to the no-reminder run, no actual improvement in what matters (state getting tracked). But narration in 6 of the 8 turns now contained a literal, player-visible line like `update_character {"target": "Bandit", "hp_delta": -8}` — the model expressing its tool-call intent as leaked text in the story itself, rather than through Ollama's real function-calling channel, where `apply_update` would have actually run. This exact leaking pattern was **not present at all** in the no-reminder run of the identical scenario — a new regression the fix introduced, not something already there. Interestingly, the *reasoning* visible inside that leaked text mostly got the target right (`"Bandit"` for enemy damage, the character's own name only for the genuinely self-inflicted turns) — weak evidence the reminder did influence the model's reasoning about *who*, just not *how* to actually invoke the tool, and arguably made the visible failure mode worse (exposed raw mechanics to the player) instead of better.
   - **Decision: reverted, not shipped.** A change that doesn't measurably improve the metric that matters (real invocations reaching `apply_update`) and introduces a new, more immersion-breaking visible defect isn't a fix, regardless of what the isolated diagnostic suggested. `server/narrator_ollama.py` and its tests are back to exactly what they were before this investigation started. The reminder's exact wording is preserved here in case a future attempt wants a documented starting point, not because it's believed to be close to correct:
     ```
     (Reminder: if this turn's outcome changes anyone's HP, inventory, or
     conditions, call update_character now. target must be whoever actually
     got hurt or changed, not simply whoever acted - if the acting character
     attacks someone else and that other creature takes the damage, target
     is that NPC's name, never the acting character's own name or 'self'.
     Only use 'self' when the acting character is the one taking damage or
     being changed.)
     ```
   - **What's actually been ruled out vs. still genuinely open, for whoever picks this up next**: ruled out — streaming as the cause (confirmed via direct A/B test against the real installed `ollama` version), and this specific reminder-based fix (confirmed via real-engine before/after testing). Still open — *why* history accumulation degrades tool-use this much, whether a structurally different intervention (e.g. two separate requests — one forcing a tool-use decision with no narration, then a second for the narration itself, rather than one combined request) would fare better, whether a different/larger local model changes this materially, and whether the same history-driven pattern affects Anthropic's Claude backend at all (still fully unverified live, pending API credits — see item 2 above).

6. **Reliability harness promoted to a real, version-controlled tool: `scripts/live_reliability_check.py`.** Closes the last bullet of this item as originally brainstormed. Runs a fixed 8-turn scenario (a faithful reconstruction of item 4's "second pass" shape — two sequential bandits, mixed call/no-call/ambiguous turns) through the real `GameEngine` against a real, live `NarratorBackend` (`--backend ollama|anthropic`, either model overridable via `--model`) — not a mock. Scores each turn by watching for the `character_update`/`npc_update` envelopes the engine actually broadcasts (the same engine-level signal the investigation itself used to measure "0 of 8" in item 5), separately flags leaked pseudo-tool-call text via a regex on the narration, and can dump a JSON report (`--out`) for diffing between runs — model vs. model, or a candidate fix's before/after, the way item 5's reminder experiment had to be done by hand. 5 new tests (`tests/test_live_reliability_check.py`) cover the scoring logic itself against a scripted fake narrator, independent of any live model. The scenario is a *reconstruction*, not a byte-exact replay — item 4's exact original action strings were only paraphrased in this file, not preserved verbatim.
   - **First real run with the new harness, live against `qwen2.5:7b` (2026-08-06): 0/8 real `update_character` calls, 0 leaked pseudo-tool-call text.** Turns 3 and 8 (pure observation/looting) correctly drew no call; turns 1, 2, 4, 5, 6 all narrated unambiguous damage to a named bandit and got no call regardless; turn 7 (cloth on a wound) is the deliberately ambiguous case and isn't scored. This closely reproduces item 4's "second pass" finding (also 0/8) on an independently-run scenario through the new tool rather than by hand, which is itself useful signal: the failure is consistent and harness-reproducible, not a one-off. Full per-turn JSON kept out of version control (a throwaway scratch run, not a fixture) — rerun `python -m scripts.live_reliability_check --backend ollama --out <path>` to reproduce.
   - **Second real run, live against `llama3.1:8b` (2026-08-06), same scenario: worse, not better — 1/7 (14%) vs. `qwen2.5:7b`'s 2/7 (29%), plus two new failure shapes.** This directly answers the "try a different/larger local model" candidate below: at the same ~7-8B size class, a bigger model was not a fix.
     - **A new, distinct correctness bug found, not just a reliability gap — and fixed.** Turns 3 and 7 *did* produce a real tool call (via the genuine Ollama function-calling channel, not leaked text) with `target` set to the literal `player_id` string (e.g. `"player-1"`) instead of `"self"` — almost certainly because `character_summary` is the character sheet's own JSON, which includes its `player_id` field, and the model echoed it back verbatim. `GameEngine._on_player_action`'s dispatch only special-cased the literal string `"self"`, so any other string — including the acting player's own id — fell into the NPC branch and silently created a phantom NPC sheet named `"player-1"`, completely disconnected from the real character. **Fixed in `server/engine.py`**: the self/NPC check now also matches `target == player_id`. Regression test added (`test_update_character_target_matching_own_player_id_treated_as_self`, `tests/test_engine.py`). This is a real, independently-worthwhile correctness fix regardless of the broader call-rate question — a silent phantom NPC is a data-integrity bug, not a missing call.
     - **A harness gap found and fixed in the same run**: turns 4 and 5 leaked `lookup_rule(category="monster", name="Goblin")` as visible prose instead of a real call, but `LEAK_PATTERN` only matched `update_character`-shaped leaks, so this went undetected in the first printed report. Broadened to catch `lookup_rule` leaks too (`scripts/live_reliability_check.py`), with a regression test (`tests/test_live_reliability_check.py`).
     - Turns 1-2 also leaked `update_character(...)` as prose (the same failure mode `llama3.1:8b` showed in the very first head-to-head comparison, turn 2, at the top of this file) — so this model shows *three* distinct failure shapes in one 8-turn run: prose-leaked `update_character`, prose-leaked `lookup_rule`, and the real-call-wrong-target bug above (turn 6 mistargeted `self` when the narration was entirely about the NPC, the same known bug from item 5).
     - **Reading on the original candidate**: doesn't rule out that a *genuinely* larger model (13B+) would behave differently — `llama3.1:8b` is the same size class as `qwen2.5:7b`, not the qualitative jump the candidate had in mind. Worth revisiting with a larger model if one gets pulled locally, but "try a same-class model" specifically is now answered: no improvement.
   - **Third experiment: the two-request split, tried for real and reverted (2026-08-07).** The most promising untried lever from item 5 — split each turn into a tool-only decision call (no narration, tools enabled) followed by a separate narration-only call (tools disabled, told what was already decided) — was implemented in `server/narrator_ollama.py` and tested live through the harness against both models on the identical scenario, exactly like the reminder-fix experiment in item 5. **Result: worse on both models, not better, plus two new defects. Reverted.**
     - **Correctness dropped for both models.** `qwen2.5:7b`: 2/7 (29%) combined-request baseline → 1/7 (14%) split. `llama3.1:8b`: 1/7 (14%) baseline → 0/7 (0%) split. Real tool-call *activity* actually went up under the split (qwen fired on 5/8 turns vs. 0/8 baseline) — the decision-only framing does get the model to attempt more calls — but targeting accuracy got worse, not better, so the net effect on the metric that matters (correct state changes) was negative.
     - **The self-vs-NPC mistargeting bug (item 5) got more pronounced, not less.** Under the split, `llama3.1:8b` defaulted to `target: self` on 5 of its 8 turns regardless of whether the narration was actually about an NPC (turns 2, 4, 6, 8 all wrongly self-targeted; only turn 7's genuine self-target was correct) — a stronger, more consistent version of the same failure the split was meant to help with.
     - **Two new defects, not present in the combined baseline.** (1) `qwen2.5:7b` turn 1 fired *two* real calls in the same turn — one correctly on the NPC, one wrongly on `self` — something the single-combined design's tighter loop didn't produce. (2) `llama3.1:8b` turn 5 produced **completely empty narration** — the decision phase correctly made no call, but the narration-only follow-up call returned zero content, a silent turn with nothing shown to the player at all, worse than a wrong tool call.
     - **A related, more subtle problem: phase 2 launders wrong phase-1 decisions into coherent-sounding but false fiction.** `qwen2.5:7b` turn 6: phase 1 wrongly applied lethal self-damage instead of NPC damage, and because phase 2 is explicitly told "don't contradict what was already decided," it dutifully narrated Torvin's own death from a blow he landed on a bandit ("your HP is now at 0 out of 10") — a wrong mechanical decision made harder to notice, not easier, because the two phases now agree with each other.
     - **A new same-family variant of the player_id-echo bug, also found and fixed.** `qwen2.5:7b` turn 5 and `llama3.1:8b` turn 3 both targeted the literal string `"Torvin Ironheart"` — the character's own *name*, also present in `character_summary`'s JSON — not just its `player_id` (the shape item 6's second bullet already fixed). **Fixed in the same `GameEngine._on_player_action` dispatch check**: `target in ("self", player_id, character.name)`. Regression test added (`test_update_character_target_matching_own_name_treated_as_self`, `tests/test_engine.py`). Independently worthwhile, kept despite the split itself being reverted — same reasoning as the player_id fix: correct dispatch for a self-referential call is right regardless of whether the model should have called at all.
     - **Decision: reverted, not shipped** — `server/narrator_ollama.py` and its tests are back to the combined single-request design, matching this project's standard from item 5: a change is only kept if it measurably improves the metric that matters under real-engine testing, not if it merely looks plausible. The engine-level dispatch fix above is the one part of this round kept, since it's a correctness fix independent of the split experiment's own outcome.
   - **Fourth experiment: quantifying the history-window tradeoff — a clean null result (2026-08-07).** `Session.max_history_messages` was pulled out of a module-level constant into a per-instance field (same default, `server/state.py`) so the harness could vary it directly via a new `--max-history-messages` flag, rather than guessing. Ran the identical scenario against `qwen2.5:7b` at three window sizes: the production default (12 messages / 6 turns, already measured at 2/7 correct, 29%), a shrunk window (4 messages / 2 turns), and zero history at all.
     - **Correctness was flat at 2/7 (29%) across all three window sizes** — 12, 4, and 0 messages produced the exact same score, with 0 real `update_character` calls at 12 and 4 messages, and only one (mistargeted) real call at 0. Shrinking or even eliminating the rolling history window bought back nothing on this scenario/model — it doesn't move the needle on tool-call correctness in either direction on its own.
     - **The zero-history condition paid real costs instead.** Two turns (7, 8) leaked pseudo-tool-call text (`update_character {"target": "self", ...}` verbatim in the narration) — 0 leaks were seen at either 12 or 4 messages. A third turn (6) leaked what reads as raw internal instruction text ("Update the character sheet for Torvin Ironheart to reflect the end of the battle.") — not caught by `LEAK_PATTERN`, which only matches the literal tool names, not paraphrased instruction-like text; noted as a known detection gap, not worth chasing with a fuzzier regex given the false-positive risk. Turn 6 also flipped the recurring monster's name from "bandit" (turns 1-5, correctly consistent) to "goblin" — exactly the "forgets what just happened" cost the rolling-history design was originally built to prevent (see "DM memory" in Current state, above), now directly observed rather than theoretical.
     - **Reading**: this complicates, rather than confirms, item 5's earlier finding that "accumulated conversation history is the real driver" of degraded tool-use. That finding came from isolated diagnostic requests measuring raw single-call invocation rate; this experiment measured engine-level, harness-scored correctness across a full scripted scenario, and found no relationship in that setup — the history-window knob is not an effective lever for this problem, and shrinking it only pays the well-understood continuity cost while buying nothing back. This closes the candidate: not "not yet tried," but tried and found not to help.
   - Remaining candidates from the original brainstorm, now cheap to test through this harness:
     - **Try a genuinely larger local model** (13B+, not yet pulled locally) — the same-size-class `llama3.1:8b` comparison didn't help, so the open question is specifically whether a bigger jump does.
     - **A visible mitigation, not a fix**: a lightweight heuristic that flags when narration contains damage/change language but no tool call actually happened that turn, surfaced to the player as a `system_message`.
     - **Case-insensitive NPC name matching**: `qwen2.5:7b`'s split-experiment run called `target="Bandit"` (capitalized) against a scenario whose narration consistently said "the bandit" (lowercase) — `Session.npcs` is a plain dict keyed by exact string, so an inconsistently-cased name from the model would silently create a second, disconnected NPC entry rather than updating the existing one. Not yet observed causing a real duplicate in these two live sessions, but the underlying risk is easy to demonstrate and cheap to defend against (normalize keys, e.g. casefold) — worth doing preemptively rather than waiting for it to actually corrupt state in play.

## Later — planned, lower priority

- **Multiplayer**: the architecture supports multiple players (`turn_order` is already a list, the transport already handles multiple connections), but it's never been exercised with 2+ concurrent connections. Worth a deliberate test pass before calling it actually supported.
- **`character_edit`** (protocol-defined, unimplemented): let a player edit their own notes/inventory directly, without DM adjudication.
- **Expand the SRD dataset** (`server/rules/srd.json`) — more monsters, spells, and full class progressions, staying strictly within CC-BY-4.0-licensed SRD content.
- **Image generation** for scenes/characters, triggered off narration beats.
- **Text-to-speech** for DM narration.

## Explicitly not doing

- Scraping or bundling copyrighted D&D sourcebook content (Monster Manual, Player's Handbook, Dungeon Master's Guide, published adventures) — not legally redistributable, even in a private repo. See `server/rules/ATTRIBUTION.md` for what's actually included and why.
- Making the repo public on any automatic trigger — that's the owner's call, not tied to any milestone here.
